# 20 — EXECUTIVE DIFFERENTIATORS

## Posicionamiento tecnico

La solucion debe diferenciar a Justech como un proveedor que no solo despliega una aplicacion, sino que entrega una plataforma institucional controlada, segura, trazable y operable.

## Diferenciadores ejecutivos

| Diferenciador | Impacto en evaluacion |
| --- | --- |
| Matriz de cumplimiento de 428 requisitos | Demuestra comprension profunda y control. |
| Blueprint tecnico completo antes de propuesta | Eleva calidad y coherencia tecnica. |
| Modelo de seguridad basado en evidencias | Reduce riesgo de penalidades y rechazo. |
| DevSecOps con escaneo y control de secretos | Alinea seguridad con entrega. |
| Azure high-level con decisiones claras | Evita prometer arquitectura sin datos. |
| Trazabilidad requisito-prueba-evidencia | Mejora aceptacion de hitos. |
| Runbooks y playbooks operativos | Facilita transferencia a INCABIDE. |
| Centro documental | Ordena manuales, evidencias y aprobaciones. |
| Modelo modular Etapa II | Permite contratacion progresiva. |
| Separacion API base vs PGR opcional | Controla alcance y costos futuros. |
| Analisis explicito de subastas | Atiende una ambiguedad critica. |
| Gobierno de datos sensibles | Alinea Ley 172-13 y datos transfronterizos. |
| Observabilidad y health checks | Muestra madurez operativa. |
| Plan de capacitacion por audiencia | Mejora adopcion. |
| Modelo de soporte con escalamiento | Alinea SLA y continuidad. |

## Mensaje para comite evaluador

Una solucion ganadora debe mostrar que Justech puede:

1. entender el riesgo institucional del SGB;
2. modernizar sin romper funcionalidad existente;
3. operar sobre Azure de forma segura;
4. entregar evidencia de cumplimiento;
5. transferir control a INCABIDE;
6. evolucionar por modulos sin bloquear adjudicaciones parciales.

## Riesgos convertidos en fortalezas

| Riesgo RFP | Respuesta de blueprint |
| --- | --- |
| Codigo fuente no disponible antes de adjudicacion | Diagnostico tecnico estructurado y evidence-first. |
| API sin alcance definido | Separacion API base, documentacion y preguntas PADF. |
| Seguridad con penalidades severas | Modelo Zero Trust y DevSecOps. |
| Azure obligatorio sin detalle | Arquitectura conceptual con decisiones pendientes claras. |
| Modulos reordenables | Backlog modular y aceptacion parcial. |
| Soporte ambiguo | Modelo de soporte y pregunta formal. |

## Resultado esperado

El blueprint permite construir una propuesta con mayor puntaje tecnico porque organiza la solucion por requisitos, no por opiniones; por evidencias, no por promesas; y por operacion sostenible, no solo por desarrollo.
